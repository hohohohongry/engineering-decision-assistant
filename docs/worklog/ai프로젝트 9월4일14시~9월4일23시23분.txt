[9월 4일 14시 시작 이후 작업 정리]

1. 후보별 장단점·Trade-off 분석 기능 구현
목표: 단순 후보 순위가 아니라, 각 후보의 강점·약점과 Trade-off를 판단자가 확인할 수 있게 함.
문제: 기존 비교표만으로는 “왜 이 후보가 유리/불리한지” 한눈에 보기 어려움.
판단: AI가 최종 후보를 정하지 않고, 확정된 정보와 비교 결과를 바탕으로 후보 특성을 정리하는 역할이 적절하다고 판단.
해결: candidate_analyzer.py 구현.
수치/상중하 비교는 Python 결과 활용
정성 비교는 기존 LLM 비교 결과 활용
후보별 강점/약점/Trade-off 출력

2. 판단조건 변화 분석 기능 구현
목표: 판단기준이나 조건이 바뀌었을 때 결과가 어떻게 달라지는지 확인.
문제: 단순 비교 결과만 보여주면 특정 조건에서만 유효한 판단으로 끝남.
판단:
우선순위/숫자 기준 변경 → Python으로 재계산 가능
“혹한 지역 판매 비중 감소” 같은 의미 해석 → LLM 필요
해결: condition_impact_analyzer.py 구현.
판단항목 중요도 변화
필수 기준값 변화
상황 변화 시나리오
핵심 원칙: AI가 결론을 다시 정하는 것이 아니라, 조건 변화가 기존 판단에 미치는 영향을 설명.

3, AI 추출항목 추천 기능 추가
문제: 처음부터 사용자가 고정된 기본항목만 선택하면 문서의 핵심 판단축을 놓칠 수 있었음.
실제 사례: 생산/조립 PDF에서 조립성·검출성이 핵심인데 기존 기본항목에서는 잘 드러나지 않음.
판단: 문서를 먼저 가볍게 읽고 “무엇을 비교해야 하는지”를 AI가 추천하고, 최종 선택은 사용자가 하는 구조가 더 적절.
해결: criterion_recommender.py 구현.
PDF 분석
중요 판단항목 4~8개 추천
추천 이유/근거 페이지 표시
사용자가 체크 해제·추가 가능
결과: 조립성, 검출성, 품질·신뢰성, 패키지 간섭, 제조·공급 복잡도 등 문서 맞춤 항목 추천 가능.

4. 후보가 사라지는 문제 해결
문제: D안처럼 문서에는 후보로 존재하지만 후보별 구체 정보가 적으면, downstream에서 후보가 사라짐.
원인: 최초 감지 후보가 아니라 “추출 결과에 남아 있는 후보”만 다시 모아 비교했기 때문.
판단: 정보가 부족한 후보도 판단 대상 자체에서는 유지되어야 함.
해결:
ai_extractor.py에서 최초 감지 candidate_names 반환
app.py session_state에 보존
비교/분석 시 확정 결과가 없어도 최초 후보 목록 유지
결과: D안도 비교표에 유지되고, 정보가 없으면 ‘-’ 또는 정보 부족으로 표시.

5. 숫자와 판단항목 의미 오매핑 수정
문제 사례: “하네스 길이 70mm 증가 + 스포일러 내부 간섭 재검토” 문장에서 패키지 간섭 값이 70mm로 잘못 들어감.
원인: AI가 같은 문장에 있는 숫자를 해당 판단항목의 수치로 잘못 연결.
판단: 숫자는 같은 문장에 있다는 이유가 아니라, 해당 판단항목을 직접 측정할 때만 사용할 수 있어야 함.
해결:
1차 추출 Prompt에 숫자-항목 의미 일치 규칙 추가
요청항목 2차 의미 검수(refine_requested_evidence) 추가
keep / rewrite / remove 방식으로 재검토
결과:
패키지 간섭 → “스포일러 내부 간섭 재검토 필요”
70mm는 패키지 간섭 수치로 사용되지 않음.

6. 상대 강점 과대해석 문제 수정
문제: 단순 긍정 정보나 구조 설명도 “상대 강점”으로 표현됨.
예: D안 “완전 사전조립 모듈 전환” → “조립성 상대 강점”
판단:
실제 후보 간 비교 결과가 있을 때만 ‘상대 강점/약점’
문서에 효과가 직접 적혀 있으면 ‘확인된 장점/부담’
구조에서 합리적으로 예상할 수 있으나 직접 확인되지 않았으면 ‘예상 장점/부담’
해결: candidate_analyzer.py에 basis 구분 추가.
relative
confirmed
inferred
결과 예:
D안 / 조립성 / 예상 장점
“사전조립 전환으로 현장 개별 조립 작업이 줄어들 가능성”
“추가 검증 필요” 표시
핵심: AI 추론 자체를 막지 않고, 사실과 추론의 근거 수준을 명확히 구분.

7. AI 추론 범위 제한
문제: 추론을 허용하면 과도한 연쇄 추론 가능.
판단: 판단자에게 유용한 1차 공학적 추론은 필요하지만, 추론을 사실처럼 표현하면 위험.
해결:
확인된 구조 → 직접적인 1차 영향까지만 추론 허용
수치, 원가, 안전성, 신뢰성 등을 임의로 확정 금지
추론 시 “가능성, 예상, 추가 검증 필요” 표현
예:
허용: 사전조립 → 현장 개별 조립 감소 가능
금지: 사전조립 → 인건비 절감 → 총원가 감소 → 수익성 향상

8. 다른 PDF로 범용성 테스트
생산/조립 PDF와 서스펜션 균열 PDF로 재테스트.
확인된 사항:
후보 보존 정상
AI 판단항목 추천 정상
숫자 오매핑 문제 개선
상대/확인/예상 구분 정상
Trade-off도 사람 판단과 대체로 유사

global/context 정보가 전부 “참고할 공통 정보”로 빠짐

예:

“실차 피크 하중이 CAE보다 큼”
→ 단순 배경정보가 아니라 판단항목의 공통 근거임.

[예상 면접 질문 및 모범 답안]

Q1. 이 프로젝트를 왜 시작했나요?
A.
현대자동차 실무면접에서 여러 부품 공용화 후보를 개발일정, 품질리스크, 호환성 등 여러 기준으로 판단하는 문제를 경험했습니다. 면접 이후 실제 설계업무에서도 여러 조건이 동시에 충돌할 때 판단 근거를 빠르게 정리하는 도구가 있으면 좋겠다고 생각했습니다. 그래서 PDF나 설계자료에서 판단 정보를 추출하고, 후보별 장단점과 Trade-off까지 정리하는 Engineering Decision Assistant를 만들기 시작했습니다.

Q2. 이 프로젝트에서 AI는 정확히 어떤 역할을 하나요?
A.
AI가 최종 후보를 선택하지는 않습니다. AI는 문서의 의미를 이해해야 하는 영역을 담당합니다. 예를 들어 판단항목 추천, 정성정보 추출, 문장형 후보 비교, 상황 변화 해석 등을 수행합니다. 반면 숫자 기준 충족 여부, 우선순위 변경처럼 명확한 계산은 Python으로 처리합니다. 최종적으로는 AI가 판단 근거를 정리하고 엔지니어가 선택하는 구조입니다.

Q3. 왜 모든 판단을 LLM에 맡기지 않았나요?
A.
설계 판단에서 계산 가능한 부분까지 LLM에 맡기면 동일 입력에서도 결과가 달라질 수 있고 검증도 어렵다고 판단했습니다. 그래서 숫자 기준, 우선순위, 가중치 등 명확한 규칙은 Python으로 처리하고, 문장 의미나 시나리오처럼 규칙화하기 어려운 부분만 LLM을 사용했습니다. AI와 deterministic logic의 역할을 분리했습니다.

Q4. 개발하면서 가장 어려웠던 문제는 무엇이었나요?
A.
단순히 정보를 추출하는 것보다, 추출된 정보의 의미를 정확하게 판단항목에 연결하는 것이 어려웠습니다. 예를 들어 “하네스 길이가 70mm 증가하고 내부 간섭 재검토가 필요하다”는 문장에서 AI가 70mm를 패키지 간섭 값으로 잘못 연결했습니다. 이를 보고 단순 추출 정확도가 아니라 ‘숫자가 해당 항목을 직접 측정하는가’를 별도로 검증해야 한다고 판단했습니다.

Q5. 그 문제를 어떻게 해결했나요?
A.
두 단계로 해결했습니다. 먼저 추출 Prompt에 숫자와 판단항목의 의미가 직접 일치할 때만 숫자를 사용하도록 규칙을 추가했습니다. 이후 1차 추출 결과를 다시 검토하는 의미 검수 단계를 추가했습니다. 각 결과를 keep, rewrite, remove로 분류해서 잘못 연결된 값은 수정하거나 제거하도록 했습니다. 이후 같은 PDF에서 70mm가 패키지 간섭 값으로 들어가던 오류가 사라졌습니다.

Q6. Prompt만 수정하지 않고 왜 2차 검수까지 만들었나요?
A.
Prompt만 강화해도 오류 빈도는 줄일 수 있지만 완전히 막기 어렵다고 판단했습니다. 특히 문서가 복잡해질수록 같은 문장 안에 여러 변수와 영향이 함께 등장하기 때문입니다. 그래서 1차 추출 단계에서 예방하고, 2차 의미 검수에서 다시 확인하는 이중 구조로 만들었습니다.

Q7. 후보 정보가 없는 경우는 어떻게 처리하나요?
A.
처음에는 추출된 Evidence가 있는 후보만 다시 모으다 보니 정보가 적은 후보가 비교 단계에서 사라지는 문제가 있었습니다. 하지만 정보 부족과 후보 부재는 다른 문제라고 판단했습니다. 그래서 최초 문서에서 감지한 후보 목록을 별도로 보존하고, Evidence가 없더라도 후보는 계속 표시하도록 수정했습니다. 정보가 부족하면 그대로 정보 부족 상태로 남깁니다.

Q8. AI가 문서에 없는 내용을 추론하는 것은 위험하지 않나요?
A.
그래서 추론 자체를 막기보다 근거 수준을 구분했습니다. 후보 분석 결과를 상대 강점/약점, 확인된 장점/부담, 예상 장점/부담으로 나눴습니다. 예를 들어 “완전 사전조립 모듈 전환”은 문서에 직접 명시된 사실이고, “현장 개별 조립 작업이 줄어들 가능성”은 공학적 추론입니다. 후자는 예상 장점으로 표시하고 추가 검증 필요를 함께 보여줍니다.

Q9. 왜 추론을 아예 막지 않았나요?
A.
이 도구의 목적이 단순 문서 요약이 아니라 엔지니어의 판단을 돕는 것이기 때문입니다. 실제 엔지니어도 자료에 명시된 사실만 읽는 것이 아니라 구조나 조건에서 영향을 예상합니다. 다만 AI가 그 추론을 사실처럼 보여주면 위험하기 때문에, 추론은 허용하되 직접적인 1차 영향까지만 허용하고 사실과 명확히 구분했습니다.

Q10. AI 추론의 범위는 어떻게 제한했나요?
A.
확인된 설계구조에서 직접 연결되는 1차 영향까지만 허용했습니다. 예를 들어 사전조립에서 현장 조립작업 감소 가능성까지는 허용하지만, 이를 다시 인건비 감소나 총원가 절감으로 연쇄 추론하지 못하게 했습니다. 수치나 안전성, 신뢰성 같은 결과도 근거가 없으면 확정하지 못하도록 제한했습니다.

Q11. 다른 문서에서도 제대로 작동하는지 어떻게 확인했나요?
A.
한 문서에 맞춘 기능이 되지 않도록 서로 다른 성격의 PDF로 반복 테스트했습니다. 생산·조립 대안 문서와 서스펜션 구조 균열 문서를 사용했습니다. 이를 통해 후보 보존, 판단항목 추천, 숫자 의미 검수, 상대/확인/예상 구분이 다른 문서에서도 작동하는지 확인했습니다.

Q12. 범용성 테스트를 하면서 새로 발견한 문제는 무엇인가요?
A.
공통정보 처리 문제를 발견했습니다. 예를 들어 “구조부 균열은 안전 이슈다”나 “실차 피크 하중이 CAE보다 크다”는 내용은 특정 후보 값은 아니지만 구조 안전성이나 검증 적합성 판단에 매우 중요한 근거입니다. 그런데 현재 구조에서는 global/context 정보가 대부분 일반 참고정보로 빠져 후보 분석에 충분히 활용되지 못했습니다.

Q13. 그 문제는 어떻게 개선할 계획인가요?
A.
정보의 적용 범위와 판단항목과의 관계를 분리할 계획입니다. 특정 후보에 해당하는 정보는 후보 Evidence로 유지하고, 전체 후보에 공통이지만 특정 판단항목과 직접 연결되는 정보는 ‘판단항목의 공통 근거’로 별도 관리하려고 합니다. 그리고 이 공통 근거를 후보 특성 분석에도 전달해 더 풍부한 예상 장단점을 만들 계획입니다.

Q14. 프로젝트를 하면서 처음 생각과 달라진 점이 있나요?
A.
처음에는 데이터 추출과 가중치 비교가 핵심이라고 생각했습니다. 그런데 여러 문서를 테스트하면서 실제 어려운 부분은 숫자 계산보다 정보가 어떤 판단항목에 해당하는지, 사실과 추론을 어떻게 구분할지, 공통정보를 후보 판단에 어떻게 연결할지라는 점을 알게 됐습니다. 그래서 프로젝트가 단순 점수화 도구에서 설계 판단 근거를 구조화하는 방향으로 발전했습니다.

Q15. 사람의 판단과 AI 결과가 다르면 어떻게 하나요?
A.
사람의 판단을 정답으로 강제하지는 않습니다. 대신 원문 근거를 가장 우선합니다. AI 결과가 달라졌을 때 원문에서 직접 확인된 사실인지, AI의 추론인지 구분해 검토할 수 있도록 만들었습니다. 사용자가 추출 결과를 수정하고 확정한 뒤 비교가 진행되기 때문에 최종 판단권은 사용자에게 있습니다.

Q16. 이 프로젝트에서 본인이 가장 중요하게 배운 것은 무엇인가요?
A.
AI를 많이 사용하는 것보다 어디에 AI를 사용하지 않을지를 정하는 것이 중요하다는 점을 배웠습니다. 계산 가능한 부분은 Python으로 고정하고, 의미 해석이 필요한 부분만 LLM을 사용해야 결과를 설명하고 검증하기 쉽습니다. 또한 AI의 추론을 없애는 것보다 사실과 추론의 경계를 명확히 보여주는 것이 실제 의사결정 지원에는 더 유용하다고 느꼈습니다.

Q17. 실제 현업에서는 어떻게 활용할 수 있다고 생각하나요?
A.
설계 대안 검토, 부품 공용화, 설계변경 검토처럼 여러 부서 자료와 판단조건을 함께 봐야 하는 상황에 활용할 수 있다고 생각합니다. PDF나 표 형태의 자료에서 후보별 근거를 먼저 구조화하고, 일정·원가·품질·성능 등의 Trade-off를 빠르게 확인하는 용도입니다. 최종 결정은 DRE나 담당 엔지니어가 하되, 판단 근거를 빠르게 정리하는 보조도구로 사용할 수 있습니다.

Q18. 이 프로젝트의 현재 한계는 무엇인가요?
A.
첫째, 공통정보가 기존 판단항목의 근거로 충분히 연결되지 않는 문제가 있습니다. 둘째, 동일 Evidence가 여러 판단항목에 중복 반영될 가능성이 있습니다. 셋째, LLM 기반 정성 분석은 표현이나 결과가 일부 달라질 수 있어 추가적인 안정화가 필요합니다. 현재는 다른 PDF를 반복 테스트하면서 이런 문제를 하나씩 분리해 수정하고 있습니다.

Q19. 완성된 프로젝트인가요?
A.
핵심 흐름은 구현했습니다. 문서 업로드, 판단항목 추천, Evidence 추출·검토, 후보 비교, 장단점·Trade-off 분석, 조건 변화 분석까지 연결되어 있습니다. 현재는 기능을 더 추가하기보다 다른 문서에서도 동일하게 작동하도록 범용성과 안정성을 높이는 단계입니다.

Q20. GitHub나 유사 사례를 참고해서 해결한 부분이 있나요?
A.
현재 프로젝트에서는 문제를 먼저 작은 단계로 나눠 직접 검증하는 방식으로 진행했습니다. 앞으로 캐싱, 구조화 출력 안정성, 평가 방식처럼 구현 수준의 문제가 발생하면 GitHub의 유사 오픈소스 사례도 참고할 계획입니다. 다만 단순히 코드를 가져오는 것이 아니라 현재 구조에 맞게 적용하고 검증하는 방식으로 사용할 생각입니다.
