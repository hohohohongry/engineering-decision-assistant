- 단순 bullet 분리는 문장 길이가 줄지 않아 효과가 부족했음
- comparison_summarizer.py 추가
- 원본 추출정보는 그대로 보존하고, 비교표에서만 AI가 핵심 내용을 1~3개 짧은 표현으로 요약하도록 구현
- 숫자·단위·증감 방향은 유지하도록 설정
- 동일 후보+동일 항목에 여러 정보가 있을 경우 하나만 표시되던 문제 수정
  → 여러 정보를 먼저 합친 뒤 AI가 중복 제거·요약
- 같은 데이터에서는 AI를 다시 호출하지 않도록 signature 기반 캐싱 적용

2. 추가정보 항목 중복 문제 개선

- 기존 항목 / 신규 항목 / 참고정보를 구분하는 기준 강화

- 한 문장에 서로 다른 의미가 섞여 있으면 기존 항목별로 분리하도록 지시
  예) 디자인 상품성 유지 + 품질리스크 감소
  → 고객체감 / 품질로 분리

3. Python 안전장치 추가
- AI가 기존 항목인 ‘품질’, ‘원가’ 등을 new_field로 잘못 반환해도 Python에서 자동 보정
- 사용자 선택항목과 이름이 정확히 같으면 무조건 existing_field로 변경
- 특정 PDF나 항목을 하드코딩하지 않고 selected_fields 기준으로 범용 처리

4. 추가정보 2차 AI 검수 구조 도입
- 1차 추출 결과를 바로 UI에 쓰지 않고, 추가정보만 다시 한 번 AI가 의미적으로 검수하도록 구현
- GitHub의 structured-output validation / re-ask 방식 참고
- 구조:
  1차 AI 추출
  → 누락항목 Recovery
  → 추가정보 2차 의미 검수
  → Python 안전장치
  → 중복 제거 및 UI 표시
- 결과:
  ‘디자인 상품성’, ‘품질·신뢰성’, ‘원가’ 등 중복 신규항목이 크게 감소
  ‘개발기간’ → 기존항목 연결
  ‘제조 복잡도’ → 신규 비교항목
  ‘검증 조건’ → 참고정보
  등으로 구분됨

5. 수정사항 미반영 문제 확인

- 서버 완전 종료 후 재실행하자 2차 검수 결과가 정상적으로 반영됨

6. ‘정보 없음’ 가짜 추출 제거
- AI가 ‘원가 정보가 명시되지 않음’ 등을 실제 추출 결과처럼 생성하는 문제 발견
- 프롬프트에서 정보가 없으면 requested_results 자체를 생성하지 않도록 강화
- Python에서도 ‘정보가 명시되지 않음 / not specified’ 등 결측 설명문을 후처리로 제거
- 결과적으로 실제 근거가 존재하는 정보만 추출 결과에 표시

- 현재는 개별 사례마다 프롬프트를 계속 수정하지 않고 오분류 사례를 모은 뒤 한 번에 개선할 예정

- 최종적으로 AI가 답을 결정하는 것이 아니라 설계자가 판단근거를 빠르게 확인하도록 지원

1. “프로젝트에서 가장 어려웠던 점은 무엇이었나요?”

가장 어려웠던 점은 AI가 비슷한 의미의 정보를 서로 다른 판단기준으로 분류하는 문제였습니다. 예를 들어 사용자가 이미 ‘고객체감’을 기준으로 설정했는데도, AI가 ‘고객가치’나 ‘디자인 상품성’을 새로운 기준으로 만드는 경우가 있었습니다.
처음에는 프롬프트를 구체화해서 해결하려 했지만 실행할 때마다 결과가 조금씩 달라지는 한계가 있었습니다. 그래서 유사한 structured-output 검증 방식을 참고해, 1차에서는 정보를 추출하고 2차에서는 그 정보가 기존 항목인지 새로운 판단축인지 다시 검수하도록 구조를 분리했습니다. 또 ‘품질’을 새로운 ‘품질’ 항목으로 만드는 것처럼 명백한 오류는 Python에서 한 번 더 차단했습니다.
이 과정에서 LLM에게 모든 판단을 맡기기보다, 의미 판단은 AI가 하고 명확한 규칙은 Python이 처리하도록 역할을 나누는 게 중요하다는 걸 배웠습니다.

이게 이번 개발에서 제일 좋은 메인 답변이야.

2. “처음부터 그렇게 설계하지 않은 이유는요?”

처음에는 한 번의 AI 호출로 추출과 분류를 동시에 처리하는 게 가장 단순하다고 생각했습니다. 실제로 기본 기능은 구현됐지만 테스트를 반복하면서 비슷한 판단기준이 계속 새로 생성되는 문제가 나타났습니다.
그래서 프롬프트를 계속 늘리는 방식보다는 문제를 추출과 분류 두 단계로 나누는 게 더 안정적이라고 판단해 구조를 변경했습니다.

이 답변 괜찮아.
처음부터 완벽히 알았던 척하지 않고, 테스트→문제 확인→구조 개선 흐름이 나옴.

3. “AI를 썼는데 왜 Python 로직도 필요한가요?”

AI는 문장의 의미를 이해하거나 ‘디자인 상품성’이 ‘고객체감’과 관련 있는지를 판단하는 데 강점이 있습니다. 반면 사용자가 이미 ‘품질’이라는 항목을 설정했는데 또 ‘품질’을 새 항목으로 생성하면 안 된다는 것은 명확한 규칙입니다.
이런 부분까지 AI에게 맡기면 결과가 불안정해질 수 있어서, 의미 판단은 AI가 하고 확실한 규칙은 Python으로 처리하도록 나눴습니다.

이건 짧고 좋음.

4. “시행착오가 있었나요?”

후보 비교표의 가독성을 높이는 과정에서도 시행착오가 있었습니다. 처음에는 긴 문장을 단순히 bullet 형태로 나눴는데, 문장 길이 자체는 줄지 않아 실제 가독성 개선이 크지 않았습니다.
그래서 원본 데이터는 그대로 보존하고, 비교표에서만 AI가 핵심 비교 포인트를 1~3개로 압축하도록 별도의 요약 단계를 만들었습니다.
단순히 화면 형태를 바꾸는 게 아니라 사용자가 실제로 비교하기 쉬워졌는지를 기준으로 다시 설계했습니다.

이것도 면접에서 꽤 좋은 사례.

5. “AI가 잘못된 정보를 만들면 어떻게 하나요?”

그래서 AI가 추출한 내용을 바로 판단에 사용하지 않도록 설계했습니다. 원문 근거와 페이지를 함께 보여주고 사용자가 확인하도록 했고, ‘정보가 명시되지 않음’처럼 실제 데이터가 아닌 값을 AI가 결과로 만들면 Python에서 제거하도록 했습니다.
최종적으로는 AI의 답을 신뢰하는 구조가 아니라, 근거를 추적하고 사람이 검토할 수 있는 구조를 만들고 있습니다.

이건 Human-in-the-loop 질문 나오면 쓰기 좋음.

6. “현재 프로젝트의 한계는 무엇인가요?”

아직 LLM 기반 의미 분류에는 변동성이 있습니다. 같은 자료에서도 추가로 찾는 정보가 조금씩 달라질 수 있고, ‘정비성’을 ‘품질’로 분류하는 것처럼 경계가 애매한 개념에서는 오분류가 발생하기도 합니다.
현재는 이런 사례를 모으고 있고, 이후 동일 자료에 대한 결과 캐싱과 오분류 사례 기반 검수 로직을 추가해 안정성을 높일 계획입니다.

한계를 숨기지 않으면서 개선 방향까지 있는 답변.

7. “최종적으로 어떤 기능까지 만들 생각인가요?”

현재는 PDF에서 판단에 필요한 정보를 추출하고, 기존 판단항목과 새로운 판단축을 정리해서 후보별 비교표로 보여주는 단계까지 구현했습니다.
다음에는 확정된 정보를 기반으로 각 후보의 장단점과 Trade-off를 설명하고, 품질이나 원가 같은 판단조건의 우선순위가 바뀌었을 때 어떤 후보의 상대적 유불리가 달라지는지도 설명하도록 확장할 계획입니다.
AI가 최종안을 결정하는 것이 아니라, 설계자가 여러 대안을 비교하고 판단할 근거를 빠르게 확인하도록 돕는 것이 목적입니다.

이건 프로젝트 설명 마지막 멘트로 거의 그대로 써도 돼.

그리고 면접에서 제일 강하게 가져갈 핵심 한 줄은 이거야.

“처음에는 프롬프트를 더 구체화하면 해결될 거라고 생각했지만, 반복 테스트에서 한계를 확인한 뒤 추출·검수 단계를 분리하고 AI와 Python의 역할을 나누는 방식으로 구조 자체를 개선했습니다.”

이 한 문장 안에 문제 발견 → 시행착오 → 탐색 → 구조 개선 → 배운 점이 다 들어가.
