# Engineering Decision Assistant

**개발자:** 홍재현  
**프로젝트 기간:** 2026.08.27 ~ 진행 중  
**프로젝트 유형:** 개인 프로젝트  

여러 설계안과 개발자료에 분산된 판단 근거를 구조화하여,  
엔지니어가 후보별 장단점과 Trade-off를 더 빠르고 일관되게 비교할 수 있도록 지원하는  
AI 기반 엔지니어링 의사결정 보조 도구입니다.

AI가 최종 대안을 대신 선택하는 것이 아니라,

> **판단에 필요한 정보를 찾고 정리하는 반복 작업을 줄이고,  
> 서로 충돌하는 조건과 놓치기 쉬운 판단 근거를 엔지니어가 확인할 수 있도록 지원하는 것**

을 목표로 합니다.

---

## 1. Project Background

부품 공용화, 설계 변경, 개발 대안 선정과 같은 엔지니어링 의사결정에서는  
원가, 품질, 개발일정, 성능, 제조성 등 여러 조건을 동시에 검토해야 합니다.

그러나 실제 개발자료에는 판단에 필요한 정보가 여러 페이지와 문장에 분산되어 있으며,

- 어떤 항목을 기준으로 비교해야 하는지 찾고
- 후보별 정보를 다시 모으고
- 수치와 정성 정보를 함께 비교하고
- 장단점과 Trade-off를 정리하는

과정에 반복적인 시간이 소요될 수 있습니다.

이를 개선하기 위해,

> **개발자료 → 판단항목 탐색 → 판단근거 구조화 → 사용자 검토 → 후보 비교 → Trade-off 및 조건 변화 분석**

과정을 하나의 Workflow로 연결했습니다.

## 2. Core Concept

### Evidence-based Decision Support

각 판단정보에 다음 내용을 함께 관리합니다.

- Candidate
- Criterion
- Value
- Unit
- Source File
- Page
- Evidence
- Scope
- Review Status

이를 통해 결과만 제시하는 것이 아니라  
**어떤 원문 근거를 바탕으로 해당 판단이 이루어졌는지 추적할 수 있도록 설계했습니다.**

### Human-in-the-loop

AI가 추출한 정보를 바로 의사결정에 사용하지 않습니다.

사용자가 직접

1. 추출 결과 확인
2. 값 및 항목 수정
3. 원문 근거 확인
4. 최종 확정

과정을 거친 정보만 후보 비교에 사용합니다.

### AI + Deterministic Logic

모든 판단을 LLM에 맡기지 않습니다.

- 문서 의미 해석
- 정성정보 비교
- 판단항목 추천
- 상황 변화 해석

과 같이 의미 이해가 필요한 부분은 AI를 활용합니다.

반면,

- 숫자 기준 충족 여부
- 정량 비교
- 우선순위 변화
- 필수 기준값 변화

등 명확한 규칙으로 처리할 수 있는 부분은 Python 로직으로 계산합니다.

## 3. Current Workflow

### ① 판단항목 탐색

업로드된 개발자료를 AI가 먼저 분석하여  
설계안을 비교할 때 중요한 판단항목을 추천합니다.

- 문서 기반 판단항목 추천
- 추천 이유 제공
- 근거 페이지 연결
- 사용자 선택 / 해제
- 사용자 정의 판단항목 추가

AI가 판단항목을 강제하지 않고  
최종 추출항목은 사용자가 결정합니다.

---

### ② AI 기반 판단근거 추출

선택된 판단항목을 기준으로 문서에서 후보별 정보를 추출합니다.

- 후보 자동 탐지
- Candidate / Global / Context 정보 구분
- 요청된 판단항목 정보 추출
- 사용자가 요청하지 않은 중요정보 추가 탐색
- 누락된 요청항목 Recovery
- 출처 페이지 및 근거문장 연결

정보가 부족한 후보도 비교대상에서 제거하지 않고 유지합니다.

---

### ③ 추출 결과 검토

AI가 추출한 정보를 사용자가 직접 검토합니다.

- 후보별 추출 결과 확인
- 값 / 단위 확인
- 원문 Evidence 확인
- 사용자 수정
- 개별 확정
- 전체 확정
- 확정된 정보만 이후 비교에 사용

---

### ④ 추출정보 의미 검수

같은 문장에 존재하는 숫자가 잘못된 판단항목에 연결되는 문제를 줄이기 위해  
추출 결과에 대한 2차 의미 검수를 수행합니다.

예:

> 하네스 길이 약 70 mm 증가  
> 스포일러 내부 간섭 재검토 필요

`70 mm`는 하네스 길이 변화량이지  
패키지 간섭의 수치값은 아니므로,

- 패키지 간섭 = 70 mm → 사용하지 않음
- 패키지 간섭 = 스포일러 내부 간섭 재검토 필요 → 정성정보로 처리

하도록 검수합니다.

---

### ⑤ 판단기준 설정

확정된 판단항목마다 역할과 중요도를 설정합니다.

- 필수 기준
- 평가항목
- 참고항목
- 판단항목 우선순위
- 정량항목 평가 방향
- 필수 기준값 설정

최종 판단기준은 사용자가 직접 설정합니다.

---

### ⑥ 후보 비교

판단항목 × 후보 형태의 비교표를 자동 생성합니다.

- 정량정보 비교
- 상 / 중 / 하 정보 비교
- 문장형 정성정보 AI 비교
- 사용자 우선순위에 따른 항목 정렬
- 필수 숫자 기준 충족 여부 표시
- 판단근거 요약

필수기준을 충족하지 못한 후보도 자동 제거하지 않고  
사용자가 전체 Trade-off를 확인할 수 있도록 유지합니다.

---

### ⑦ 후보별 장단점 · Trade-off 분석

확정된 정보와 비교 결과를 기반으로  
각 후보에서 얻는 것과 감수해야 하는 것을 정리합니다.

분석 결과의 근거 수준을 다음과 같이 구분합니다.

#### Relative

후보 간 실제 비교를 통해 확인된

- 상대 강점
- 상대 약점

#### Confirmed

문서에서 효과가 직접 확인된

- 확인된 장점
- 확인된 부담

#### Inferred

확인된 설계구조에서 합리적으로 예상할 수 있지만  
문서에서 직접 검증되지는 않은

- 예상 장점
- 예상 부담

예상 결과에는 추가 검증이 필요함을 별도로 표시합니다.

AI 추론은 확인된 사실에서 직접 연결되는  
**1차적인 공학적 영향까지만 허용**하도록 제한합니다.

---

### ⑧ 판단조건 변화 분석

현재 조건에서의 비교 결과만 보여주는 것이 아니라  
판단조건이 달라졌을 때 무엇이 달라지는지도 분석합니다.

#### 판단항목 중요도 변화

특정 판단항목의 중요도가 증가하거나 감소했을 때

- 강점 반영 정도
- 약점 반영 정도

가 어떻게 변하는지 분석합니다.

#### 필수 기준값 변화

숫자로 정의된 필수조건이 변경될 경우  
Python으로 기준 충족 여부를 다시 계산합니다.

#### 상황 변화 시나리오

예:

> 혹한 지역 판매 비중이 크게 낮아진다면?

과 같이 단순 계산으로 처리하기 어려운 조건은  
LLM이 기존 판단근거와 연결하여 영향 방향을 분석합니다.

## 4. Design Principles

### AI가 최종 후보를 선택하지 않는다

본 도구는 자동 추천 시스템이 아니라  
**엔지니어의 판단 준비를 지원하는 Decision Support Tool**을 목표로 합니다.

### 정보 부족을 숨기지 않는다

문서에 근거가 없다면 임의로 값을 생성하지 않고  
정보 부족 상태로 유지합니다.

### 사실과 AI 추론을 구분한다

문서에서 직접 확인된 내용과  
AI가 설계구조를 바탕으로 예상한 영향을 구분하여 표시합니다.

### 후보를 임의로 제거하지 않는다

정보가 부족하거나 일부 필수기준을 충족하지 못하더라도  
후보 자체를 자동 제외하지 않고 사용자가 최종 판단하도록 합니다.

## 7. Current Issues & Next Steps

### Common Evidence 구조 개선

현재 특정 후보에만 속하지 않는 Global / Context 정보가  
일반 참고정보로 분류되는 경우가 있습니다.

하지만 다음과 같은 정보는 단순 참고정보가 아니라  
특정 판단항목의 중요한 공통 근거가 될 수 있습니다.

예:

- 구조부 균열은 안전 관련 이슈
- 실차 피크 하중이 기존 CAE 입력보다 높음

향후

> **일반 참고정보**

와

> **기존 판단항목의 공통 근거**

를 분리하여 후보 특성 분석에도 활용할 예정입니다.

### Evidence 중복 반영 검토

동일한 Evidence가 여러 판단항목에 동시에 반영되면서  
같은 정보의 영향이 과도하게 표현되는 경우가 있는지 추가 검증하고 있습니다.

### 판단항목 의미 중복 검토

AI가 추천한 판단항목 중 의미적으로 유사한 항목이 동시에 생성되는 경우를  
다양한 문서를 이용해 검증하고 있습니다.

### Generalization Test

특정 문서에 맞춘 규칙이 되지 않도록  
서로 다른 유형의 엔지니어링 개발자료를 이용해 반복 테스트하고 있습니다.

## 8. Development Approach

프로젝트 구현 과정에서는 기능을 한 번에 완성하기보다

> **구현 → 실제 문서 테스트 → 오류 발견 → 원인 분석 → 구조 수정 → 다른 문서 재검증**

방식으로 개발하고 있습니다.

단순 Prompt 수정으로 문제를 덮기보다  
반복되는 오류가 특정 문서의 문제인지 구조적인 문제인지 구분한 후 수정하는 것을 원칙으로 합니다.

## 9. Project Goal

최종 목표는 AI가

> **“어떤 후보가 가장 좋은가?”**

를 대신 결정하는 것이 아닙니다.

대신 엔지니어가

> **“각 후보에서 무엇을 얻고 무엇을 감수해야 하는가?”**  
> **“어떤 근거 때문에 현재 판단이 만들어졌는가?”**  
> **“조건이 바뀌면 어떤 판단요소의 영향이 달라지는가?”**

를 더 빠르게 확인할 수 있도록 지원하는 것을 목표로 합니다.
